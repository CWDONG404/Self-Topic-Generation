# 架构说明

## 服务边界

- `frontend`：只负责界面、表单校验、SSE 消费和 PDF/原文出处展示。
- `api`：负责数据校验、持久化、文件访问、密钥管理和任务控制。
- `worker`：负责文档解析、Embedding 与出题流水线；默认并发为 1，避免本地模型和 OCR 争抢内存。
- `postgres`：保存业务数据、pgvector 向量与 LangGraph 检查点。
- `redis`：保存 Celery 队列和短期实时通知，不作为任务状态的权威来源。

## 出题图

出题流程由 LangGraph 执行，但图节点必须返回结构化状态，不能让 Agent 自由决定终止条件。

1. 蓝图节点从重点资料归纳考点，再将考点映射到正文 chunk。
2. Supervisor 使用最大余数法把文档百分比换成整数配额。
3. 出题节点只接收检索出的 evidence ID 和正文，不接收整本文档。
4. 服务端依据 evidence ID 补齐真实页码和坐标，模型无权提供坐标。
5. 审题节点独立作答；答案、引用或题意不合格时返回明确反馈。
6. 每题最多返修两次，整卷最多补题三轮。
7. 严格去重仍不足时才允许同考点相似题，完全重复永不接受。

## 引用稳定性

原文件以 SHA-256 内容哈希标识，每次上传产生不可变版本。PDF chunk 保存一页或多页上的矩形列表；非 PDF chunk 保存结构化 block ID 与字符区间。题目引用版本 ID，而不是易变化的文件名。

## 任务与进度

业务任务和事件先写 PostgreSQL，再向 Redis 发布通知。SSE 客户端使用事件序号重连，因此刷新页面或 Redis 短暂重启后仍可补发遗漏进度。LangGraph 使用任务 UUID 作为 thread ID，从数据库检查点恢复。

## 安全边界

- 默认仅监听本机，不提供身份认证。
- 文件名不会直接拼接为磁盘路径；服务端生成存储键并验证 MIME。
- DOCX 仅作为压缩文档读取，不执行宏或嵌入对象。
- 模型密钥采用认证加密保存，只向前端返回掩码。
- 本地模式在任务启动前校验所有角色配置，任何云端角色都会使任务被拒绝。
